Якісна документація покриває щонайменше рівні Система та Компонент

ЯК vs ЧОМУ

Обидва важливі — але "чому" старіє краще

ЯК побудовано

  • Діаграми (C4, UML)
  • API-контракти
  • Моделі даних
  • Топологія розгортання

ЧОМУ так побудовано

  • ADR — записи рішень
  • Розглянуті компроміси
  • Обмеження та драйвери
  • Відхилені альтернативи

SSD — SYSTEM SPECIFICATION DOCUMENT

ЩО система повинна робити

  • Мета та обсяг — яку проблему вирішує система
  • Функціональні вимоги — функції, сценарії використання, user stories
  • Нефункціональні вимоги — продуктивність, безпека, масштабованість
  • Інтерфейси — зовнішні системи, API, формати даних
  • Обмеження — технологічний стек, бюджет, регуляції

SSD відповідає: "Що ми будуємо і для кого?"

SDD — SOFTWARE DESIGN DOCUMENT

ЯК система побудована

  • Огляд архітектури — високорівнева структура та патерни
  • Декомпозиція модулів — компоненти, відповідальності, межі
  • Дизайн даних — схема БД, потоки даних, стратегія зберігання
  • Дизайн інтерфейсів — API-контракти, протоколи, формати повідомлень
  • Обробка помилок та логування — режими збоїв, відновлення, спостережуваність

SDD відповідає: "Як це працює всередині?"

SSD vs SDD

Специфікація vs Дизайн — вони доповнюють одне одного

C4 МОДЕЛЬ

4 рівні масштабування — як Google Maps для вашої архітектури

L1: Контекст
система + користувачі + зовнішні
→
L2: Контейнери
додатки, БД, черги
→
L3: Компоненти
модулі всередині контейнера
→
L4: Код
класи, інтерфейси

Більшості команд достатньо L1 + L2. L3 для складних сервісів. L4 рідко малюють вручну.

ЯК ГЛИБОКО ЗАНУРЮВАТИСЬ?

L1 + L2
Достатньо для більшості проєктів — чіткі межі, схема розгортання
+ L3
Додати, коли контейнер складний — багато внутрішніх модулів
+ L4
Рідко потрібний — автогенерується з коду (UML class diagrams)

ADR — ARCHITECTURE DECISION RECORDS

Документуйте ЧОМУ за кожним важливим рішенням

Назва: ADR-007: Використовувати PostgreSQL замість MongoDB
Статус: Прийнято
Контекст: Нам потрібні ACID-транзакції для платежів. MongoDB ненадійно підтримує мультидокументні транзакції на нашому масштабі.
Рішення: Використовувати PostgreSQL 16 з JSONB-колонками для гнучких даних поряд з реляційними таблицями.
Наслідки: Команді потрібна експертиза в SQL. Отримуємо сильну узгодженість, зрілий інструментарій та перевірений шлях масштабування.

СТРУКТУРА ADR

Легка, послідовна, версіонована

Контекст
в чому проблема?
→
Рішення
що обрали
→
Наслідки
що з цього випливає
→
Статус
запропоновано / прийнято / застаріло

Зберігається в git: docs/adr/ADR-007-use-postgresql.md

ЧОМУ ADR ВАЖЛИВИЙ

  • Запобігає повторним дискусіям — "ми вже вирішили це і ось чому"
  • Контекст для онбордингу — нові розробники розуміють логіку, а не лише код
  • Контекст для AI — AI читає ADR і генерує код, що поважає рішення
  • Аудиторський слід — доказ, що рішення були свідомими, а не випадковими

DoD — DEFINITION OF DONE

Чеклист, який кожна задача повинна пройти перед тим, як вважатись "зробленою"

Приклад DoD

✅ Код перевірений та затверджений (code review)
✅ Unit-тести написані та проходять
✅ Інтеграційні тести зелені в CI
✅ Документація оновлена
✅ Немає відомих критичних багів
✅ Задеплоєно на staging

DoD спільний для всієї команди — однаковий стандарт для кожного

DoR — DEFINITION OF READY

Чеклист, який кожна задача повинна пройти перед початком роботи

Приклад DoR

✅ User story чітко написана
✅ Критерії приймання визначені
✅ Залежності ідентифіковані
✅ Дизайн / макет затверджений
✅ Оцінена командою

DoR запобігає "розберусь по ходу" — зменшує втрати та переробки

DoR vs DoD

Ворота на вхід, ворота на вихід

🚪
DoR
Чи достатньо зрозуміла задача, щоб почати?
→ робота →
✅
DoD
Чи справді задача завершена?

Без DoR починаєш незрозумілу роботу. Без DoD випускаєш незавершену.

ACCEPTANCE CRITERIA

Конкретні, тестовані умови, яким повинна відповідати функція

User Story: Як клієнт, я хочу скинути пароль

AC1: Користувач отримує лист для скидання протягом 60 секунд
AC2: Посилання для скидання діє 24 години
AC3: Новий пароль повинен відповідати вимогам (8+ символів, 1 велика літера, 1 цифра)
AC4: Після успішного скидання користувача перенаправляє на логін
AC5: Недійсні або прострочені посилання показують зрозуміле повідомлення про помилку

ЯК ПИСАТИ ЯКІСНІ ACCEPTANCE CRITERIA

Given / When / Then — BDD-формат

Given  користувач запросив скидання пароля
  And  лист для скидання було надіслано

When   користувач натискає посилання протягом 24 годин
  And  вводить валідний новий пароль

Then   пароль оновлюється
  And  користувача перенаправляє на логін
  And  старий пароль більше не працює

Конкретно. Тестовано. Без двозначності.

AI ТА АРХІТЕКТУРНА ДОКУМЕНТАЦІЯ

AI прискорює документування — але не замінює архітекторів

AI може

✅ Генерувати Mermaid-діаграми з тексту
✅ Створювати чернетки ADR з нотаток зустрічей
✅ Будувати скелети SDD з коду
✅ Виявляти недокументовані компоненти

AI не може

❌ Приймати архітектурні рішення
❌ Розуміти бізнес-обмеження
❌ Оцінювати компроміси у вашому контексті
❌ Замінити peer review
