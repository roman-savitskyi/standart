WHY DOCUMENTATION MATTERS

"It's not optional — it's infrastructure"

  • Onboarding: weeks without docs → days with docs
  • Knowledge preservation: developers leave, docs stay
  • Technical debt: undocumented code = code no one dares touch
  • Compliance & audits: ISO, contracts, legal requirements
Починаємо з базового питання: навіщо писати документацію? Ключова ідея — документація це інфраструктура, не "приємно мати". Техборг без доків = чорна скринька. Питання залу: хто вважає документацію опціональною?

NEDEN DOKÜMANTASYON ÖNEMLİDİR

DOCUMENTATION AS CODE

Treat docs like you treat source code

  • Stored in git alongside the code
  • Written in plain text — Markdown, AsciiDoc
  • Reviewed via pull requests
  • Built and deployed via CI/CD
  • Versioned and released with the product
Docs as Code = документація живе поруч з кодом у git. Якщо код ревʼюється, тестується, версіонується — чому документація ні? Інструменти: MkDocs, Docusaurus, Sphinx. Docs в тому ж PR що й код — ніхто не забуде оновити.

WHAT AI DOES WELL

Documentation tasks AI handles reliably

  • Docstrings from function signatures and types
  • README from codebase structure analysis
  • API docs from code / OpenAPI schema
  • Changelogs from git history
  • Translation and simplification of existing docs
  • Diagrams from text descriptions (Mermaid)
AI справляється з механічними завданнями документування. Докстрінги з сигнатур — майже ідеально. Changelog з git history — дуже практично для релізів. Mermaid: можна попросити AI намалювати архітектуру по тексту. Переклад + спрощення — корисно для технічного письма.

DOCUMENTATION FIRST

Write the README before writing the code

  • Forces you to design the interface before implementation
  • AI reads your README and generates a working skeleton
Зворотній підхід до розробки: спочатку README, потім код. Описуємо інтерфейс, поведінку, очікуваний результат — і лише тоді даємо AI генерувати скелет. Це змушує думати про дизайн перед реалізацією. Бонус: README вже готовий до релізу.

GARBAGE IN — GARBAGE OUT

The quality of your docs = the quality of AI-generated code

❌ Vague input

// function that does stuff
function process(data) {}

AI output: generic, possibly wrong

✅ Precise input

/**
 * Validates email per RFC 5322.
 * @throws {ValidationError} if invalid
 */
function validateEmail(email: string): boolean {}

AI output: correct, typed, edge-cases handled

Найважливіший слайд: якість вхідних даних = якість AI-коду. Перший приклад — function process(data): AI нічого не розуміє. Другий: JSDoc з типами і винятками — AI генерує правильний, типізований код з обробкою помилок.

GİRDİ KALİTESİ = ÇIKTI KALİTESİ

Dökümanlarınızın kalitesi = AI'nın ürettiği kodun kalitesi

❌ Belirsiz girdi

// bir şeyler yapan fonksiyon
function process(data) {}

AI çıktısı: genel, muhtemelen yanlış

✅ Kesin girdi

/**
 * RFC 5322'ye göre e-posta doğrular.
 * @throws {ValidationError} geçersizse
 */
function validateEmail(email: string): boolean {}

AI çıktısı: doğru, yazılmış, kenar durumlar ele alınmış

WHAT AI CANNOT REPLACE

The human layer that must remain

  • Domain knowledge — business context, edge cases, user intent
  • Architectural decisions — the WHY, not just the WHAT
  • Accountability — someone must own the output
  • Ethics & judgment — when to say "this shouldn't be built"
  • Review — AI output always needs a human in the loop
Важливий баланс — AI це інструмент, не заміна. Доменні знання: AI не знає вашого бізнесу і ваших користувачів. Архітектурні рішення: ЧОМУ ми так зробили — це не в коді, а в голові людини. Відповідальність: хтось повинен підписати рішення. Ревʼю — завжди людина в петлі, це не опціонально.
